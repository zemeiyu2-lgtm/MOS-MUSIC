# ADR-0019｜歌曲分类 V1.1（四维 / 多归属 / 前台只显示四维）

- 状态：**Frozen**
- 日期：2026-09-23
- 关联：ADR-0015（前台与候选目录）、ADR-0018（独立定位）

## 背景

V2.0 的候选层已经带有 `front_tags.theme` / `front_tags.scene`（录入期初分类），
但分类从未被正式定义：它是身份还是入口？能不能多属于几类？前台该看到多少？

分类一旦复杂化，就会出现「先想好分类，再决定歌曲是什么」的反向塑造 —— 这正是本项目一直避免的。

## 决策

取消复杂分类体系，正式采用**四维**：

| 维度 | 回答的问题 | 类型 | 归属 |
|---|---|---|---|
| 01 主题 | 歌曲主要表达什么 | 标签集合 | **多归属** |
| 02 处境 | 人在什么情况下可能需要这首歌 | 标签集合 | **多归属** |
| 03 场景 | 在哪里使用 | 标签集合 | **多归属** |
| 04 音乐 | 歌曲本身的音乐属性（难度 / 速度 / 音域 / 拍号 / 适合视唱 / 适合群体歌唱 / 适合个人练习） | 属性组 | 单组多字段 |

**分类原则**：

> **分类只是帮助用户找到歌曲。它不是歌曲的身份。**
> 一首歌可以同时出现在多个分类中。不要让歌曲只能属于一个类别。

**前台设计原则**：用户看到的是 主题 / 处境 / 场景 / 音乐。
用户**不**看到 `calibration`、`source_required`、`governance`、`W01`、`W02` —— 除非进入后台。

## 词表来源（反虚构）

分类词表**只能来自内容层**，程序不得硬编码，也不得自行扩充：

- 主题：沿用候选层既有 13 词（`content/candidates/index.json#themes`），**未新增**；
  产品方向里提到的示例词（感谢 / 信靠 / 悔改 / 奉献 / 爱 / 圣洁 / 使命）登记为
  `pending_extension_candidates`，**未经人工裁决前不得用于任何歌曲标注**（CI-0032）。
- 处境：取自曲库详情层既有字段 `formation.emotion`（词取自记录本身）；
  产品方向示例里没有来源的词同样登记为待裁决项。
- 场景：候选层 `scenes` ∪ 详情层 `scenes`。
- 音乐：难度取详情层 `discipleship.difficulty`；拍号 / 速度 / 音域取单元 `score`；
  「适合视唱 / 群体歌唱 / 个人练习」目前**没有任何来源 ⇒ 一律留空**并标明「尚未标注」。

## 实现

- 词表与原则：`content/taxonomy/index.json`
- 分词结果（派生）：`content/taxonomy/assignments.json`，由 `tools/taxonomy.js` 从既有记录推导，
  **每条带 `derived_from`**；源值不在词表内 → 记入 `unmapped` 交人工裁决。
- 校验：`node tools/taxonomy.js --check`（词表闭合 / 多归属 / 计数一致）
- 前台：诗歌本按维度筛选（命中集合任一项即算匹配）、歌曲页显示四维（空维度显示「尚未标注」）。

## 实测现状（2026-09-23）

- 覆盖候选 100 首；主题 100 首有值、场景 100 首有值、处境 **5 首**（详情层有 `formation.emotion` 的 5 首）、
  音乐 **10 首**（详情层有难度值）；多归属歌曲 10 首。
- 其余留空**是真实状态，不是遗漏**：候选层没有处境与音乐字段。

## 后果

- 分类不会成为新的研究体系，也不会产生排名或推荐；
- 未来扩词表必须走人工裁决，工具只报告 `unmapped`。
